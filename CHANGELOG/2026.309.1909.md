# 2026.309.1909 — feat(bed): add the disposable browser lease R10 bed

## Summary

Add `check-pod-crabbox-browser-runs`, the disposable R10 bed for
`pod-crabbox-browser`. The image's own checks are BUILD-scope: a build
container never launches the browser, so they cannot prove the thing this
variant exists for — Chromium runs inside a live Crabbox lease with its
sandbox ENABLED.

The bed follows the four sibling `pod-crabbox*` beds in the check system's
three-step gate shape:

1. **ABSENCE** — Chromium is installed but not running: no Chromium process,
   nothing listening on the DevTools port, and no browser profile. The lease
   also refuses a freshly generated key, and a venue that does not answer fails
   the step instead of reading as "nothing started yet".
2. **PERFORM** — the shared bootstrap consumes the read-only `/crabbox`
   inputs (`authorized_keys`, `lease.env`, `bootstrap.sh`), then the lease user
   renders `about:blank` through the image's own `/usr/local/bin/crabbox-browser`
   over the lease's own SSH path.
3. **PRESENCE** — the captured DOM is a rendered document; a persistent
   Chromium answers its DevTools endpoint with its sandboxed children in a
   nested PID namespace; no running Chromium carries a sandbox-disabling flag;
   and the lease holds over SSH as `crabbox` on 2222 with passwordless sudo and
   `/usr/local/libexec/crabbox/ready` exiting 0.

The change is one new `pod:` deploy entity in `charly.yml`. The image, its
candy and its published tags are unchanged.

### Negative control for the sandbox assertion

The normal run cannot exercise the sandbox assertion's failure mode, so on a
live disposable deploy built from the same image I ran the same detector
against two launches and then removed the probe:

```text
$ grep -vE '^\+|^\+ ' /tmp/sandbox-control.out | grep -E 'NEGATIVE CONTROL|POSITIVE CONTROL|detector found|detector child pid=1167|detector child pid=1252'
=== NEGATIVE CONTROL: --no-sandbox launch ===
detector found=0
=== POSITIVE CONTROL: Chromium default sandbox ===
detector child pid=1167 levels=2 NSpid=1167	1
detector child pid=1252 levels=3 NSpid=1252	14	1
detector found=1
```

The `--no-sandbox --disable-setuid-sandbox` launch produces no nested PID
namespace, so the detector reports `found=0` and the assertion FAILS. The
default launch produces `found=1` (a nested `NSpid` of two and three levels),
so it PASSES. The probe deploy was then torn down:

### Anomaly and RCA (R1)

The first run of this bed (local, before the first push) failed PRESENCE; the
absence and perform steps passed. A fresh RCA named two mechanisms, both
introduced by this change:

1. The perform step's stderr redirect created `/tmp/crabbox-browser.log` owned
   by `root:root`. The presence step launches Chromium as `crabbox` and
   redirected to the same path, so that shell refused with `Permission denied`
   and no browser ever started; `curl` then failed on every retry. That is the
   truncated `bash:` the summary showed.
2. Even with the browser running, the detector read
   `/proc/<pid>/ns/pid` and `/proc/<pid>/ns/user`, which need
   `CAP_SYS_PTRACE`; podman's default capability set excludes it (measured:
   `ls: cannot read symbolic link '/proc/268/ns/pid': Permission denied`).

Root fixes, both in this change:

- the probe launch writes `/tmp/crabbox-browser-probe.log`, a path the absence
  step removes and `crabbox` owns;
- the detector reads the world-readable `NSpid` field from
  `/proc/<pid>/status` and requires at least one zygote/renderer in a nested
  PID namespace.

The missed control was that the presence step had never been executed on a
live deployment before the first bed run. The negative and positive controls
above now exercise its failure mode. The re-run on the committed tree passes.
